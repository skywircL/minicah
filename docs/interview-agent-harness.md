minicah 项目面试讲述与深挖问答

这份稿子面向 Agent Harness 团队的全栈 AI Builder 岗位，以当前 minicah 仓库的代码、文档和已留存实验为依据。采用先总述、再分点展开的方式：先练完整项目介绍，再根据面试官的问题选择具体回答。它是一份练习材料，不需要在面试现场从头背到尾。

以下第一人称是供你练习的表达。仓库可以证明项目具备哪些实现和实验，不能证明你的个人分工、实际使用过哪些 AI 编程工具、用户数量和实习安排。这些部分需要与你的真实经历一致。动态模型路由、跨会话长期记忆、主动智能闭环，以及生产环境的完成检查，正文均按后续设计来讲。

**先总述：请你完整介绍一下这个项目。**

我这个项目叫 minicah，是用 TypeScript 和 Node.js 做的一个轻量、插件化的 Coding Agent Harness。简单说，它负责把模型、工具、上下文、权限和执行记录组织起来，让一个编码任务能够实际执行，而且执行过程可以检查，出问题之后能够定位原因。

我关注的问题是：模型已经能提出很多看起来合理的操作，但产品要真正可用，还需要回答一些更具体的问题。比如它准备修改哪个文件，用户到底批准了哪次操作，文件有没有被其他人改过，运行到一半退出以后能不能接着看历史，以及模型说完成的时候，任务是否真的完成。这些事情如果全部混在一个循环里，开始能跑，但后面很难扩展，也很难评估。

所以这个项目主要围绕三件事展开。

第一件事是把执行底座搭起来。我做了插件契约、依赖验证、资源所有权和生命周期管理，把模型、工具、Session、Context 和终端交互放到独立插件里。内核负责组织这些能力。一次任务开始时会拿到固定的配置和插件版本快照，让模型参数、工具定义和执行实现保持一致；同时，已经失效的审批仍然会在派发前被拦住，不能因为任务开始得早就继续使用。

第二件事是把一次 Agent 执行做得可追踪。模型的实际请求会先保存再发送，工具调用要经过参数验证、宿主策略和必要的审批，执行意图也会先持久化。文件修改使用读取时的内容哈希检查版本，防止把别人刚改的内容覆盖掉。发生异常时，我会区分明确失败和结果未知；恢复历史不会直接重做一个可能已经发生的写操作。

在上下文这块，我把完整历史和模型下一次真正看到的内容分开了。完整事件保留，模型使用的是一个可以压缩的投影。长工具结果可以裁剪，较早历史可以摘要，但工具调用及其结果要按完整消息组处理，不能拆散配对，也不能隐藏未结算调用。

第三件事是给这些能力建立评测和诊断链路。项目里既有不调用真实模型的链路校准，也有真实模型运行。最近一轮完整扩展集基线评测，是用 deepseek-flash 跑一百五十条受控变体，一共八百五十八次试验，七百三十八次通过，一百二十次失败。按试验次数统计，通过比例约百分之八十六。不过这些题来自十个父家族，属于开发集，我不会把这个数字当成线上泛化能力。

这轮评测最有价值的地方，是发现了一个比较典型的失败：多轮任务压缩历史以后，模型没有执行新的修改，就直接返回 completed。我沿着请求、工具轨迹和最终文件状态去检查，确认当前任务和工具都传到了模型，然后针对历史表达和任务措辞做了对照实验。在这个场景下，把“完成上述修改后”明确写成回复 completed 的前提，效果比只强调回复格式更好。

这个结果也让我看到 Harness 还需要补的一层：模型停止生成，只能说明这次循环结束了，不能自动证明业务目标已经达到。目前项目已经有独立评测来发现这个差异，也做了窄场景的状态检查与续接实验，但通用的生产完成检查还没有接入，我会把这两个阶段分开讲。

所以我觉得这个项目和岗位最直接的结合点，是我已经把一个 Agent 从模型调用推进到了可运行、可观察、可评估的工程形态。现在证据最充分的是执行可靠性、Context 和 Eval。后面如果继续做模型路由、长期记忆或者主动任务，也可以接在这个底座上，用同一套记录和评测验证收益。

**一、项目定位与整体架构**

**1．为什么做这个项目，你想解决的具体问题是什么？**

我想解决的是 Agent 在真实执行中的不确定性，以及这种不确定性出了问题以后难以定位。拿修改配置来说，用户觉得是很简单的一句话，但 Agent 实际要理解目标、读取文件、判断是否需要改动、获得权限、写入、验证，再给出结果。任何一步缺少明确状态，最后都可能只剩一句“已经完成”。

所以我把第一阶段的目标收得比较具体：做一个能够读代码、修改受控工作区、执行受审批命令、保存会话并进行评测的 Coding Agent。先让一个任务从输入到结果形成可检查的过程，再逐步扩展能力。

如果面试官追问有没有用户需求验证，我会如实说明，目前仓库能支持的是可运行原型、演示和本地评测，不能据此证明已有规模化用户。下一步我会找有具体编码任务的人试用，观察他们在哪里接管、哪里不信任结果，而不是只问他们觉得界面好不好用。

**2．你怎么解释 Harness、Agent Loop 和模型的关系？**

我的理解是，模型负责根据当前材料提出下一步，Agent Loop 负责不断执行“获取上下文、请求模型、调用工具、接收结果”的循环，Harness 则负责让整个过程有明确的运行规则。

例如模型提出修改文件，循环可以把这个动作派发出去，但 Harness 还要确认：这个工具是否存在，参数是否合法，当前权限是否允许，审批是否绑定到这次调用，日志能否可靠提交，以及异常以后怎么恢复。它还要让模型、工具和上下文策略能够替换，否则每改一个策略都得改整个应用。

在这个项目里，模型服务和循环服务都由插件提供，内核并不写死某个模型。这样做的实际价值是，后面比较不同模型或者压缩策略时，可以尽量保持其他条件一致，避免把模型变化和运行器变化混在一起。

**3．你能顺着一次请求讲清楚整个链路吗？**

可以。用户在 CLI 输入任务后，系统先在当前 Session 中开始一次 run，固定这次运行使用的配置、服务绑定和工具目录。接着记录用户输入和任务状态，再从已提交历史构造模型上下文。

每次请求前会检查上下文容量，必要时压缩。模型适配器先生成实际请求材料，日志持久化以后再发送。模型返回工具调用时，Host 为这些调用分配自己的标识，再交给共享工具管线。管线进行参数、策略、审批和执行检查，把结构化结果提交到 Session，下一轮模型就能够看到结果并继续。

如果模型没有继续调用工具，当前循环会接受正常停止；如果工具结果不确定，就停止后续操作并要求核对。这里有个我会主动说明的限制：正常停止目前不包含通用业务验收。正因为评测独立检查最终状态，才发现了“循环结束但任务没完成”的问题。

**4．为什么要插件化，会不会把一个小项目设计得过于复杂？**

我做插件化主要是为了控制变化的影响范围。模型接入、工具权限、上下文策略、CLI 交互和日志持久化的变化频率不同，如果都放在一个对象里，后面很难单独替换，也容易出现谁创建资源、谁负责关闭说不清楚的问题。

但我也没有把所有能力都扩成复杂平台。内核只保留服务索引、依赖验证、资源所有权、作用域和生命周期。具体的模型与工具留在插件里，接口版本采用明确匹配，首版也没有做任意状态迁移。

我承认插件化增加了契约和生命周期成本。这个成本只有在需要切换模型、替换执行底座、复用 Session 或比较策略时才有收益。如果只是一次性的脚本，我会用更直接的结构。这个项目的目标本来就是 Harness，所以这些边界值得做清楚；它们也能通过失败路径测试来验证，不只是画在架构图上。

**5．Runtime、Session、Run 三层分别解决什么问题？**

Runtime 管共享能力和整体生命周期，例如模型插件、工具注册和执行服务。Session 管一段持续的交互历史，例如用户输入、工具记录和上下文投影。Run 是一次任务执行时拿到的版本和绑定快照。

举个例子，用户今天在同一个会话里先让 Agent 理解仓库，再让它修改配置，这可以是同一个 Session 里的两次 run。两次任务之间更新模型参数，新的 run 使用新配置，但旧任务的历史仍然保留。

有一个实现细节容易讲错：当前资源作用域主要是 Runtime 和 Session，并没有另外做一套通用 Run 资源作用域。服务对象可以按 run 惰性构造和缓存，但需要跨任务保留的连接、历史等状态，还是放在相应插件的闭包中，并注册清理方法。这样资源寿命和调用快照就不会混成一个概念。

**6．你最重视哪些失败边界？**

我最重视的是“系统不知道自己到底做没做成”的情况。明确拒绝比较好处理，明确成功也比较好处理，最难的是写操作已经派发，但结果还没可靠记录，或者进程被取消以后清理没有确认。

另一个边界是不同状态被错误合并。比如工具参数不合法，不等于用户拒绝；文件没变化，不等于没有执行能力；模型回复 completed，也不等于目标状态正确。如果把这些都压成一个成功或失败字段，后续既不好恢复，也很难判断应该修模型、工具还是评测。

所以我倾向于保留原始事件和具体状态，再做面向用户的简化展示。用户可以只看到“需要核对这次写入”，但开发者应该能够查到执行意图、调用标识、权限决定和提交状态。这也是后面能够做真实 badcase 分析的基础。

**二、工具执行与可靠性深挖**

**7．工具调用为什么不能直接交给模型生成的参数去执行？**

因为模型输出只是一次建议，真正的执行责任在 Host。就算返回的是合法 JSON，也可能字段错了、工具选错了，或者这个调用在当前权限下不允许。

项目使用 Ajv 做 JSON Schema 校验，工具管线再处理策略和审批。一个真实失败案例是，模型调用 write_file 时混进了编辑工具才需要的 oldText 字段。JSON 能解析，但 schema 不允许这个额外字段，所以调用在进入审批之前就被拒绝了。模型随后却报告 completed，这就暴露了参数出错后的恢复问题。

这个案例我不会描述成“用户拒绝了写入”，因为实际没有发生审批拒绝，也不会说成接口服务异常。诊断必须沿着真实的阶段看。后续如果加恢复逻辑，应把明确的参数错误反馈给模型，让它修正调用，而不是把所有失败都当作可以直接重复的请求。

**8．你的审批设计和弹一个确认框有什么区别？**

我把审批看成对一项具体操作的授权。用户同意修改某个文件，并不代表同意下一次任意修改。因此审批需要绑定到本次 run、工具、参数和相应的配置及版本信息，并且具有有效期和单次消费语义。

例如用户看到的是把开发环境超时从三十改成十，审批以后如果调用参数换了，或者运行配置已经变化，旧审批就不能继续使用。执行必须走匹配的审批回复和调用入口，不能因为日志里曾经出现过 allow，就认定现在有权限。

这也影响恢复。重放日志时可以知道当时发生过什么权限决定，但历史记录不是一张可无限重复使用的通行证。对于用户而言，这个设计的意义很直接：他批准的事情和最终执行的事情应当能够一一对上。

**9．文件修改怎样避免覆盖用户刚刚做的改动？**

项目采用读取时拿到内容哈希、写入时检查预期哈希的方式。模型读取文件以后，工具会返回文件内容和版本证据。修改请求需要带上这份证据，Host 才能判断文件是不是仍然处于模型看到的状态。

假设 Agent 读完文件，用户又在编辑器里改了一行，此时继续基于旧内容覆盖就有风险。哈希不一致时应该让调用失败并重新读取，不能悄悄把用户的改动抹掉。文本编辑还要求 oldText 只匹配一次，避免相同片段出现多次时修改错位置。

但我会把保证讲得准确：这属于版本校验和受控写入设计，不等于文件系统级的多参与方事务。面对任意外部进程的并发修改，不能只凭一个哈希参数就宣称解决了所有竞态。更严格的协作编辑还需要进一步明确锁、提交协议和冲突处理。

**10．为什么工具执行前要先保存执行意图？**

这样才能在进程异常退出以后知道，某个操作究竟有没有进入可能产生副作用的阶段。项目会先把执行意图持久化，再调用工具，完成后再记录结果。

最典型的窗口是文件已经改完，但结果还没成功写入日志，进程突然退出。恢复时如果只看见没有成功结果就重新执行，可能造成重复操作。先有执行意图，至少可以识别这是一项需要核对的调用，而不是把它当成完全没开始。

我不会把这套机制说成通用的 exactly-once。日志和外部副作用通常没有一个共同事务，仍然可能出现结果未知。项目选择把未知状态保留下来，停止依赖它的后续操作。对于能提供幂等键或目标状态检查的外部系统，可以继续加强恢复，但这些能力必须由具体业务来定义。
**11．Session 日志怎样保证恢复后看到的是可信记录？**

项目把一批事件作为一个事务写入 JSONL。事务里带有会话标识、连续序号和校验信息；恢复时先验证这些信息以及状态转换，再重建会话状态。正常提交也是先在候选状态上验证整批事件，写入达到指定同步级别以后，再切换内存状态并通知订阅者；CLI 默认要求 fsync 完成。

这样可以避免一种情况：界面已经收到成功通知，但日志实际上还没有提交。流式文字则是另一条临时展示通道，它让用户及时看到进展，但不承诺每个片段都持久化。真正的完成状态需要以提交后的事件为准。

这里也有工程边界。fsync 比仅写入系统缓存提供更强的本地同步语义，但它不是跨机器复制，也不代表所有故障下都绝不丢数据。校验信息主要用于发现损坏和不一致，也不是防恶意篡改的签名机制。当前日志主要面向本地项目，还没有磁盘分页索引和完整的长期归档能力。如果会话规模持续增长，这会是后续必须处理的问题。

**12．恢复会话和重新执行任务有什么区别？**

恢复会话首先是读取已提交的事实，重建历史、配置引用和上下文，让用户知道之前发生了什么。它本身不需要再次请求模型，也不应该重新执行历史工具。

继续任务则是一个新的执行决定。开始之前，要先处理上次留下的不确定调用。如果上次只准备了操作但没有派发，和操作已经派发却没有确认结果，处理方式就不一样。后者可能需要查询实际文件状态，或者根据外部服务的幂等信息核对。

项目还考虑了一个更细的空隙：模型响应已经记录了工具调用，但工具还没进入管线，进程就退出。只检查已登记的工具会漏掉这部分，所以模型响应里的子调用标识也要参与恢复检查。这类细节对演示不显眼，但决定了恢复功能在异常路径上是否可信。

**13．PTC 在你的项目里做了什么，适合什么任务？**

PTC 可以理解为让模型生成一段受控程序，用程序来组织多个工具调用。例如需要读取几个文件、筛选相关字段、汇总一个结果，如果每个小步骤都要模型来回决策，会增加交互次数。程序能够处理其中比较确定的循环、分支和聚合。

我在项目里主要做的是 Host 编排和安全边界：模型程序运行在隔离后端中，能够调用哪些 Host 工具由显式 bindings 限定；这些子调用仍然经过同一个工具管线，也保留父子关系和执行证据。PTC 不会因为藏在程序里面，就跳过参数验证或权限检查。

当前首版只开放只读工具，PTC 进程不直接挂载工作区；默认 CLI 仍然走普通模型工具调用。它适不适合一个场景，需要比较同模型、同任务和相同能力边界下的成功率、请求数、总用量和时延。我不会仅因为程序调用更集中，就宣称已经验证了普遍降本。

**14．普通工具调用已经能并发，PTC 还有必要吗？**

它们解决的问题有重合，但不完全一样。普通工具调用可以让模型在一次响应里提出多个独立操作，项目也会并发派发。PTC 的区别在于，程序可以根据前一个工具结果决定下一步，完成一些确定的中间处理，再把精简结果交回模型。

不过 PTC 也引入了程序生成错误、控制协议、隔离执行和调试成本。对于只有一两个文件读取的任务，直接工具调用可能更简单。对于需要多次条件查询和结果聚合的只读任务，才更值得比较。

评测时尤其要避免给普通工具模式人为串行化、却让 PTC 并发，这样得到的收益没有说服力。我会保持工具集合、模型配置和资源限制尽量一致，把并发能力也对齐，再观察程序化编排本身带来的变化。

**15．Docker、macOS 原生隔离和插件作用域是不是一回事？**

它们分别处理不同层面的边界。插件作用域主要决定一个服务绑定到谁、哪些注册项可见、资源什么时候释放。这是同一个宿主进程里的组织机制，不能用来限制恶意插件任意访问操作系统。

真正的执行隔离由 Docker 或 macOS Seatbelt 后端提供。项目负责把命令、工作区副本、网络和资源策略转成后端配置，并确认进程退出和清理情况。Docker 命令操作的是过滤后的临时工作区副本，默认关闭网络，也不会自动把修改回写宿主项目。

macOS 首版禁止创建子进程，适合一些单进程脚本和 PTC，但不能当成 Docker 资源配额的等价替代。默认 Host 模式则没有操作系统隔离。因此面试时我会说实现了多种执行后端的适配和边界管理，而不会把容器或系统沙箱本身说成自研成果。

**16．热更新为什么要考虑正在运行的任务？**

因为执行到一半时改变规则，会让一个任务失去一致性。比如模型看到的是旧工具定义，真正执行时却换成了新实现；或者用户根据旧参数批准操作，后面用另一套配置执行。这些问题会直接影响结果和审计。

项目把更新分成不同层次。普通动态配置更新生成新版本，已有 run 继续使用旧快照，后续 run 才采用新配置。不过已有审批可以因配置发布而失效，派发时仍要重验，固定快照不代表继续保留旧授权。插件替换则要先验证候选、阻止新的 run 进入、等待已有任务结束，再切换并释放旧资源。

有些排他资源必须先停旧实例再启动新实例，这时启动失败就不能承诺无损回退。清理超时也不代表资源已经销毁，系统会保留问题并要求重启。我觉得热更新的关键价值在于说清楚何时生效、失败后是什么状态，而不是对所有情况都承诺无感切换。

**三、Context 工程与记忆深挖**

**17．你的 Context Engineering 具体体现在哪里？**

我主要做的是管理模型每一步能够看到的信息。完整 Session 是事实记录，Context 是根据这些事实构建的工作视图。这样既能保留审计和恢复需要的原始材料，又能控制真正发送给模型的长度和结构。

每步调用前，系统会测量上下文压力，保留必要的约束和近期信息，裁剪过长工具结果，必要时用摘要替换连续的历史消息组。工具结果投影只保留模型需要的结构化内容，避免把 value 和审计 evidence 里的重复正文都发送一次。

这里我会明确区分“支持受保护信息”与“自动识别所有关键约束”。当前已有保护信息和约束的机制，但没有一个通用系统能从用户自然语言中自动提取、更新全部长期约束。这个能力还需要额外设计和评测。

**18．为什么不直接保留最近若干轮对话？**

因为最近若干轮未必包含真正决定正确性的内容。比如用户在很早之前说过不要修改生产配置，后面很多轮都在讨论开发环境，简单截断就可能丢掉持续约束。另一种情况是工具调用在一条消息里、结果在下一条消息里，机械切消息数量可能把配对拆开。

项目以完整消息组为基本单位，一个模型响应以及它对应的工具结果要一起处理。并发工具可能以不同顺序完成，但进入模型上下文时仍然按照原调用关系组装。尚未结算的调用也不能被摘要隐藏。

这并不意味着结构完整就保证语义完整。结构约束解决的是可机械验证的问题，重要事实有没有被摘要遗漏，仍然需要看后续任务能否继续完成。压缩策略最终应当用行为结果验收，而不能只看文本缩短了多少。

**19．自动压缩怎么触发，为什么分两步？**

当前策略先测量请求规模，同时为下一次输出预留空间。接近配置的压力阈值时，优先处理冗长的工具结果；如果仍然需要缩小历史，再请求模型生成摘要。

先裁剪是因为很多工具输出的中间部分很长，但对下一步决策未必有用。项目使用明确的裁剪配方，保留必要结构和截断标记，不是把整个结果对象直接截成坏 JSON。摘要则要选择连续、完整、已经结算的历史消息组，并保留最新用户输入和近期尾部。

这套顺序的好处是先尝试成本较低、比较可控的处理，再使用模型。摘要请求本身同样消耗上下文、时间和 tokens，所以不能为了节省后续请求，把压缩过程当成没有成本。当前摘要复用同一个模型服务，并没有接入专门的低成本摘要模型路由。

**20．你怎么防止摘要本身出问题？**

我先做能确定验证的检查：摘要必须正常结束，不能包含工具调用，文本不能为空，而且本地估算要比原来的历史更短。如果生成期间 Context 已经变化，这份摘要也不能直接覆盖新状态。

实现上会检查 Surface 的版本和内容，真正提交时还会核对预期的事件位置及当前视图。只有替换成功提交，新的摘要才成为模型下一次使用的材料。失败时保留原来的历史，并记录压缩失败，而不是把一次无效摘要当成已经释放了容量。

但这些检查不能证明摘要语义完全正确。更完整的验证需要专门构造包含约束变更、否定表达、目标回滚、失败操作和未完成事项的长轨迹，观察压缩后任务还能不能做对。这个语义评测方向可以在现有记录底座上扩展，但不能冒充目前已经有完整的自动正确性证明。

**21．你如何估计 token，估不准怎么办？**

当前使用的是带余量的本地估算，并结合兼容请求的供应商 usage 做校准。它不是精确 tokenizer，因此我会把它解释为容量管理信号。特别是中文、代码、结构化工具定义和普通英文的字符分布不同，不能简单把字符数或者字节数等同于 token 数。

校准也有条件：模型定义和请求参数、工具等非消息部分需要匹配，才能参考最近一次普通请求的输入用量，再结合新旧输入估算的差值调整。摘要调用不参与这个校准，也不会因为某次供应商数字偏低就向下压低本地保守基线。这样至少能避免跨模型、跨工具配置套用一个过期比例。

发送前会检查输入估算和输出预留是否能装进配置的窗口。如果服务端在开始输出前明确拒绝了上下文长度，可以尝试压缩；但只有 Context 版本确实推进、估算长度确实减少，才允许有限重试。

网络超时或输出到一半断开，不属于这个明确拒绝的路径，因为不能确定请求有没有执行以及产生多少用量。还有一种情况是最新用户输入本身就过大，或者必要的完整消息组无法放入窗口，这时应该明确报容量不足，不能靠反复生成摘要陷入循环。

**22．持久化会话和长期记忆有什么区别？**

持久化会话解决的是同一段交互如何保存、查看和恢复。长期记忆还需要决定跨会话保留什么、在什么任务里召回、如何更新冲突事实以及何时忘记。当前项目完成的是前一部分，以及同一会话中的上下文压缩。

如果继续做长期记忆，我会先把稳定偏好、项目事实和历史经验分开。比如输出语言偏好相对稳定，但某个文件的当前字段值很容易过期，不能因为昨天记住了，就跳过今天的实际读取。每条记忆应该带来源、作用范围、时间、可信度和有效状态。

存储可以先用结构化数据，关键词和范围过滤也可能足够，等召回需求明确以后再引入向量检索。关键是记忆是否可验证、是否过期、有没有越过使用范围。把聊天记录全部存进向量数据库，并不能自动解决这些问题。

**23．如果设计记忆的召回与遗忘，你会怎么做？**

我会让召回围绕当前任务和权限范围展开。先筛选同一用户或项目允许使用的内容，再考虑相关性、新鲜度和来源证据，最后在有限的上下文预算里选择少量材料。召回内容作为带来源的参考进入上下文，不直接变成新的高优先级指令。

遗忘也需要分情况。临时状态可以设置有效期，明确被用户纠正的旧事实应该被标记为失效，用户要求删除的内容还要同步处理索引和派生副本。对于互相矛盾的记忆，不能只凭向量相似度选一个看起来最接近的答案，需要检查来源和更新时间，必要时重新询问或者读取实际状态。

评测上，我会同时看该记住的有没有召回、不该带入的有没有混入、旧事实纠正后是否还干扰决策，以及使用记忆后任务成功率有没有提升。这些是后续方案，目前没有宣称跨会话记忆已经上线。
**四、Eval 设计与真实结果深挖**

**24．你的评测到底测模型，还是测 Harness？**

两类都测，但要分开报告。模型侧关心它能不能完成用户任务，例如理解仓库、按约束修改、继续多轮任务。Harness 侧关心系统契约，例如工具是否正确验证参数，拒绝以后有没有停止，恢复时有没有重复副作用，以及版本切换是否一致。插件平台还有依赖、作用域和生命周期等独立检查。

如果只用一个总分，很容易把问题归错。模型没有调用工具，可能是动作选择问题；工具参数不合法后模型没有恢复，是调用与错误处理问题；运行器丢失了实际请求，则是工程链路问题。修复对象不同，不能简单换一个更强模型就算解决。

另外，离线 fixture 只证明工具、Session、判分和报告链路能够跑通。它按固定脚本做动作，不能代表模型理解任务的能力。真实模型成绩必须来自明确选择模型 provider 的实验，这个区别我会在介绍结果时先说明。

**25．一个任务怎样才算做对，为什么要三层判分？**

我把验收拆成结果、行为和回复三层。结果看最终文件或者函数行为是否正确；行为看执行过程是否遵守权限、写入范围和其他约束；回复看公开约定的格式和可核验字段，是否真正完成还要与结果层交叉核验。关键必需判据失败，整个任务就不能算通过。

例如模型输出一个完全合法的 completed JSON，但文件没有改，回复格式可以对，结果必须判错。反过来，文件改对了，但最后多加一段说明，而调用方要求严格 JSON，这也可能使整个集成失败，所以回复契约不能完全忽略。

还有一种情况，模型改过保护文件，后来又恢复。只看最终文件差异可能发现不了，因此行为层需要工具轨迹。三层分开以后，我们既能知道用户目标有没有达到，也能知道为什么一个看似正确的结果仍然不符合交付要求。

**26．Ground Truth 是标准答案吗，你怎样判断裁判本身可靠？**

我把 Ground Truth 理解成可执行的验收契约，不要求所有正确解都长成同一份参考代码。比如配置修改可以检查字段值和保护文件，函数修复可以通过明确输入、输出与异常行为来判断。

我也会测试裁判。新增题目先跑正确参考，再跑专门违反条件的反例。反例应该被预期的判据检出，其余判据必须全部通过；如果是沙箱启动失败或者日志缺失，不能把这种失败当成裁判识别错误实现的能力。

一百五十条变体做过一百五十次正参考和三百次反例校准，共四百五十次，这个阶段没有调用模型 API。它说明所声明的规则在这些参考和反例上能够运转，但不等于业务语义已经通过独立人工审查。当前人审仍保留待完成状态，我不会把自动校准说成人工验收。

**27．三十八条金种子和一百五十条变体是什么关系？**

三十八条是覆盖用户任务、运行可靠性和插件平台的金种子候选，其中十四条用户任务、十六条 Harness 契约、八条插件平台契约。当前是可审阅候选，不是三十八条都已经完成正式人审的最终金标。

一百五十条则是从十个父家族扩出来的受控变体，包含原来的二十条和新增的一百三十条。扩展方向包括边界条件、权限拒绝、对抗材料和多轮对话。它们增加了同一类机制的压力，但共享父题结构，统计上不能当成一百五十个完全独立的业务场景。

这些数据都是公开开发集，也没有新增独立留出家族。后面验证泛化时，我会增加新的父任务、不同仓库和未参与调试的留出集，并且按父家族划分，避免同一模板的轻微变体同时出现在开发和测试两边。

**28．真实评测的结果怎么讲最准确？**

我会先讲实验条件和分母，再讲分数。项目留存的这轮实验使用 deepseek-flash，普通题四十八条，每题三次；高风险题一百零二条，每题七次。多轮对话整体算一次试验，因此总共八百五十八次，其中七百三十八次通过、一百二十次失败，没有排除项。

按所有试验直接计算，通过比例是百分之八十六点零一；给每道题相同权重，宏平均是百分之八十六点六七；按父家族再平均，是百分之八十七点八一。它们回答的问题不同，所以我不会把几个数字混着用。

我更关心的是稳定性。一百五十道题里，九十九道在各自重复协议下全部通过。但普通题跑三次，高风险题跑七次，这个九十九比一百五十不能直接叫统一的 pass 的 k 次方。采用共同的三次组合估计，全部成功的指标约百分之七十五点七，能看出“有时能做对”和“持续做对”之间的差距。

**29．pass@k 和 pass^k 怎么区别，为什么同时看？**

pass@k 关心给若干次机会，至少一次成功的概率；pass^k 关心同一任务重复 k 次全部成功的可靠性。前者更接近探索性任务里允许挑一次结果，后者更接近用户希望交给 Agent 就稳定完成的需求。

举个例子，一道题七次运行成功五次。按现有七个样本抽三次，只要一次成功就算过，那么 pass@3 是百分之百，因为失败样本总共只有两个。但如果要求三次都成功，组合估计是十除以三十五，大约百分之二十八点六。

项目用的是有限重复样本的组合估计，不是把通过率简单乘三，也不是直接把五除以七再立方。有排除或证据不足的重复时，对应指标也不能随便用剩余样本冒算。对于会写文件的 Agent，多试几次还可能增加成本和副作用风险，所以我不能只展示最好的一次。

**30．你如何保证每次评测互不污染？**

每个 trial 创建独立工作区和 Session，初始文件与日志彼此分离，并保留版本和内容哈希。多轮任务内部共享会话，因为它需要测试连续执行；不同重复之间重新初始化，这两种“共享”要区分清楚。

判分材料也需要和模型输入隔离。隐藏 grader、参考答案和未来轮次完整题面不能提前作为当前用户消息给模型。对函数任务，Agent 结束以后，Host 再在独立评分沙箱中验证候选函数；这一步不代表模型自己运行了测试。

当前真实评测没有向模型开放 shell，因此不能把成绩宣传成已经验证了完整的自主安装依赖、运行测试、定位失败再修复的编码闭环。它验证的是当前工具集合和约束下的任务能力。以后如果开放命令，应当另立协议，因为模型获得的能力、风险和成本都改变了。

**31．怎么从一百二十次失败里面找到真正值得修的问题？**

我会先按可观察机制归类，再确定优先级。最新复核把一百二十次失败去重分成五类：五十九次必要修改没有执行，十二次写了错误实现，十五次没有形成要求的实际审批拒绝，十七次只有最终回复失败，还有十七次题面和判据需要裁决。

这个分类和三层判分不一样。结果、行为、回复可能在同一次 trial 同时失败，数量不能相加；这里按主要机制让每个失败只进入一类，才方便决定工程优先级。

对我来说，最优先的是用户目标没有完成却报告成功。其次要解决已经发现的验收契约歧义，否则改模型还是改题面都说不清。然后才是具体代码边界和回复格式。排序也会结合风险与出现范围，不能只根据某一类数量最多就机械决定全部研发方向。

**32．讲一个最能体现你排查能力的具体案例。**

我会讲 GM-D19，也就是“文件没改，却说完成”的那个案例。任务本身很简单：第一轮读取开发和生产配置，第二轮把开发环境 timeout 从十改为三十，第三轮再改回十。生产环境的六十必须保持不变，修改前需要重新读取，最后按约定返回 JSON。

在固定摘要后的续接场景里，第三轮七次全部失败。失败时没有任何工具调用，模型直接返回 completed，开发配置仍然是三十。这个现象说明问题发生在真正执行修改之前，但还不能直接说原因是模型忘记了目标。

所以我先检查原始请求，确认最新用户指令、摘要中的当前值和可用工具都确实发送了。这样至少排除了这几个样本里“任务没传过去”或者“工具被隐藏”的解释。接着检查工具事件与实际文件，确认不是写入失败或者日志漏记，而是根本没有派发读写。

到这一步，我能确定的是模型提前选择了结束，不能确定它内部到底怎么理解了 JSON 模板。我把这个区别保留下来，后续实验只检验可以控制的输入因素，不把一个听起来合理的心理解释当成根因结论。

**33．你是怎么设计对照实验，而不是反复改提示碰运气的？**

我先固定失败轮之前的真实历史前缀，只重放第三轮，每次都创建独立运行环境和一致的文件状态。这样不用每次重新采样前两轮，避免把上游波动混进来。不同实验条件按预先计划交错执行，尽量减少执行时间顺序带来的影响。

第一轮做了六组，每组八次。其中原样组通过两次；把最后一句改成“完成上述修改后，最终回复只返回 JSON”，八次全过；只删除摘要中“前两轮已完成”这句话，只通过一次；换回完整历史也是八次全过。

这些结果里，有一个很关键的反面证据：删除“已完成”并没有支持最初的猜测。所以不能事后讲成“我发现摘要里的完成字样导致模型收尾，删掉就解决了”。完整历史有效也不能说明是哪一个历史成分起作用，因为内容、长度和角色序列同时发生了变化。

为了把有效改动拆开，第二轮又分别测试“最终回复”和“完成上述修改后”。同期原样六次全失败，只加“最终回复”通过两次，只加完成前提六次全过。另一道把端口改成零的任务，也出现了同方向改善。这让我对工程改进的判断更具体：在这些配置续接任务里，明确完成前提比单独强调回复阶段更有支持。

**34．看到八次全过，你能说问题已经解决了吗？**

我只能说这个改动在本次受控样本中有效，不能说普遍解决。样本数量很小，任务又集中在配置修改，服务端缓存、执行时间等也可能让重复之间并不完全独立。八次全过依然有很大的统计不确定性。

而且这次实验固定了已有历史，并没有重新评估模型自己生成摘要的过程。原来的固定摘要通过率低，也不能直接外推成自动压缩算法普遍有问题。我们验证的是特定上下文表达与当前指令之间的行为关系。

下一步应该把有效改动放到新版本协议里，增加不同类型的续接任务，并保留旧题作为诊断回归。同时分别评估任务表达改善和 Harness 完成检查的收益。当前生产 Agent 没有因为这次实验自动获得一个通用修复，原始基线也没有被覆盖。
**35．如果让你真正修复“没完成就结束”，你会怎么改？**

我会在模型提出结束和系统确认完成之间，增加可信的业务检查接口。对于目标明确的配置任务，调用方可以提供公开目标和保护范围，检查文件是否达到要求，以及不应该变化的内容是否保持不变。

如果目标已经满足，可以接受合法的无需修改。目标没满足、执行状态确定、也没有真实审批拒绝时，可以给出实际状态反馈，允许一次有界续接。如果已经被拒绝，或者写入结果未知、保护文件发生了异常变化，就不能靠自动重试继续推进。

项目已经做过一个实验原型：对原样组的六次失败，检查公开目标状态后追加一个用户轮次，六次都修复成功。但额外用了二十七次 API 请求和四万一千九百四十四 tokens，所以我保留首次失败，并单独记录补救成本。

这个原型还没有接入生产循环，也不是通用完成判断器。后续需要解决接口由谁提供、如何验证保护范围、流式完成文字怎样展示，以及检查失败时的状态语义。尤其不能把隐藏测试答案反馈给模型，也不能用“调用过写工具”替代任务正确性。

**36．有没有遇到其实是评测写错，而不是模型做错的情况？**

有需要裁决的情况，我不会在证据不足时直接说评测一定错了。一个例子是字段迁移：题面说删除 retries、增加 retry、保留其他字段，但没有明确只迁移根对象。模型把嵌套字段也迁移了，判据却要求嵌套字段不变，这就需要先把业务范围说清楚。

另一个例子是目标值本来已经满足。题面要求“修改前重读”，模型没有修改，最终状态也对，但 grader 无条件要求一定调用读取工具。这里到底要求每次都确认新鲜状态，还是仅在写入前确认，是两个不同的产品契约。

还有一次，搜索工具确实返回了两个单行 JSON 文件的完整内容，但判据只认可 read_file。搜索通常不保证读完全文，因此也不能无条件放宽；应该根据公开要求和实际证据判断是否等价。

这些情况一共涉及十七次待裁决失败，当前仍包含在原来的一百二十次里。正确处理方式是澄清规则、冻结新版本、重新校准和评测，不能看到结果以后临时删掉失败或者改分。

**37．除了不执行，还有什么代码层面的真实错误值得讲？**

一个比较有代表性的错误，是导出选择函数里用 in 运算符判断成员是否存在。任务要求只选择对象自身的键，in 却会把原型链上的键也算进去。有的补丁注释甚至写着只检查自身属性，但实际代码仍然使用 in，说明文字解释不能替代行为验证。

另一类是只修最显眼的分支，例如处理了显式空数组，却漏掉隐式分支的私有成员过滤、排序规则或者返回形状。还有补丁把名称数组改成对象数组，下游消费端仍然按名称处理，局部看起来更完整，整体接口却被破坏了。

这些案例让我倾向于把需求拆成输入分支、输出契约、消费者依赖和边界值逐项检查。当前任务协议不允许模型运行命令，我不会批评它为什么没擅自跑测试；可以先验证静态契约核对是否有帮助，再为允许执行验证工具的场景单独做实验。

**五、模型路由与成本策略的岗位追问**

**38．这个岗位很重视模型路由，你的项目已经实现到哪一步？**

目前实现的是模型服务抽象、配置版本和 Provider 替换，以及模型请求、用量和执行结果的记录。每次 run 使用固定的模型配置，还没有根据难度、成本和时延动态决定模型的路由器。

我觉得这部分基础的价值是，后面增加路由时可以保留稳定的执行和观测接口，也能记录这次为什么选某个模型、使用哪一版策略。现在改一个 model 配置或者替换模型插件，只能叫切换模型，不能叫智能路由。

如果接下来由我负责，我会先定义几类能明确验收的任务，建立固定模型基线，然后做简单、可解释的规则路由。等有足够的任务与结果数据以后，再考虑学习型路由。这样能够判断收益到底来自模型选择，还是其他同时变化的工程因素。

**39．路由器第一版具体会看哪些信号？**

我会先看任务类型、可用工具、上下文长度、操作风险，以及历史相似任务的表现。比如只读定位、简单格式转换和跨文件行为修复，对推理能力和出错成本的要求并不相同。用户要求的响应时限也应该进入决策。

第一版可以先用规则，把低风险、容易确定性验证的任务分到成本较低的模型，把复杂依赖分析或者代价高的修改交给更合适的模型。这里的“合适”要从本地评测得出，不能仅凭型号名称或者参数规模判断。

我不会完全依赖模型自报的信心，因为它的信心也可能不准。模型对任务难度的判断可以作为一个特征，但需要用实际成功率校准。规则未覆盖的任务先走保守默认路径，并记录原因，这样后续才知道哪些类别值得补数据。

**40．为什么不能所有请求先用便宜模型，失败再升级？**

这种策略只有在失败容易发现、失败成本可接受、状态能够安全继续的情况下才合适。只读检索失败，通常还可以换模型继续；写操作已经发生但结果不确定时，盲目升级再跑可能重复修改，也可能把用户拒绝过的操作重新提出。

此外，先便宜再升级会产生两次模型调用和更长的历史。有些任务小模型反复尝试的总费用与时延，可能超过一开始就用更合适的模型。因此我会比较整段任务的实际开销，而不是只看第一次请求的单价。

实现上，升级点应该选在状态明确的边界，并沿用当前可信上下文和权限规则。模型变强不代表权限变大。对于明确参数错误、业务检查失败、网络状态未知和用户拒绝，策略也应当分别处理，不能统称为失败后重试。

**41．怎样证明路由真的省钱，又没有牺牲体验？**

我会用固定模型策略作为对照，比较相同任务集合下的端到端通过率、行为合规、每个成功任务的成本，以及延迟的中位数和高分位数。还要记录升级比例、重复请求和用户接管，因为这些都会影响实际体验。

成本要包含普通推理、摘要、路由判断和重试，不能只计算最终成功的那次。计算每个成功任务的摊销成本时，也要纳入失败任务的消耗，并同时报告成功率，避免删掉昂贵失败后得到一个好看的数字。用量缺失不能按零计。当前项目有 token 和请求记录，但没有完整的货币计费层，也没有累计费用硬上限，所以这部分还需要增加模型价格、计费规则与预算策略。

离线可以先比较候选规则，准备独立留出任务；有真实用户以后，再在允许的范围内做影子评估或小比例上线。路由效果也应按任务家族拆开看，防止整体成本下降，却让某一类关键任务的失败率明显升高。

**六、主动智能与 Skill 的岗位追问**

**42．你如何理解主动智能，准备从哪个具体场景切入？**

我理解的主动智能，是在用户明确允许的范围内，系统能够根据状态变化判断是否需要行动，并把结果核验清楚。重点不只是定时唤醒一个模型，而是触发是否有意义、行动是否适当、用户是否真的受益。

如果基于 minicah 做第一版，我会选一个窄场景，例如用户订阅某次验证任务后，检查运行结果是否出现新的失败，并给出相关定位信息。先做只读分析和有价值的提醒，再逐步考虑用户预先授权范围内的修改。

当前项目没有这个完整产品能力。配置文件变化后自动加载新配置，是运行器的事件响应，不等于已经能够感知用户意图、主动推送或自主完成业务任务。可以复用生命周期和记录能力，但触发器、订阅管理和通知策略都需要另做。

**43．主动 Agent 怎样避免重复执行和频繁打扰用户？**

我会先让事件有稳定标识，再把事件是否已处理、处理到哪一步持久化。重复收到同一事件时，先查看已有状态，而不是重新启动一段完整操作。连续相似变化还需要合并、冷却和明确的停止条件。不过事件去重不能保证外部动作恰好发生一次；通知已经发出但回执没保存，或者写入完成但日志提交失败，仍然需要目标系统的幂等支持或状态核对。

提醒之前要判断是否有新的、可行动的信息。比如同一个已知失败没有变化，通常不需要反复通知；如果失败原因变了、问题恢复了，或者需要用户决定下一步，就值得提醒。用户还应该能够查看为什么触发、暂停订阅或者撤销范围。

如果允许动作，则继续沿用工具权限、版本快照和不确定结果处理。触发次数不能直接当作活跃度，通知点击也不能直接当作价值。评测要看有价值提醒的比例、漏掉的重要变化、重复动作、打扰频率以及用户最终节省了多少操作。

**44．你会怎样做自主闭环和自我进化？**

我会先把自主闭环限制在可验证任务里：感知变化，判断是否满足触发条件，形成计划，在授权范围执行，再检查结果并记录。如果结果不明确，就停止或转交用户，而不是为了表现自主一直继续。

自我进化第一阶段更适合做成受评测约束的策略迭代。系统收集失败样本，形成新的提示、Skill 或路由规则候选，在固定回归和独立任务上验证，达标后再发布新版本，同时保留回滚依据。

我不会一开始就让 Agent 在线随意改自己的权限规则或把成功一次的补丁直接推广。因为失败归因可能错，评测也可能存在歧义。minicah 目前已有版本、轨迹和评测的部分基础，但自动收集、候选生成、发布门禁和线上回滚还没有组成现成功能。这是可以往前做的路线，不能作为已经交付的成果。

**45．Skill 在这个项目里有什么实现，和普通提示有什么关系？**

项目里已经有显式的 Skill 注册目录，可以记录版本、说明、正文和附属文本资源。列表接口只返回摘要，需要时再通过接口取得正文或附属资源，并复用分层目录与 run 快照的规则。

它解决的是内容组织、可见范围和版本一致性，为按需加载留出接口。但当前 CLI 没有把完整的自动发现、选择和加载流程接进去，也没有 Skill 自动生成和进化机制。所以我会说完成了基础注册与读取能力。

如果做成产品，我会让 Skill 对应重复出现的一类任务，明确适用条件、操作步骤、输入输出契约和验收方式。验证它有没有价值，应该比较同模型、同工具条件下启用与不启用的表现，同时检查误触发和额外上下文开销。文档写得长、步骤列得多，不自动代表任务成功率更高。
**七、个人贡献与产品交付的追问**

**46．你用了 AI 写代码，怎样体现自己的工程能力？**

这部分应该用我实际做过的决策来回答，而不是只强调生成了多少代码。AI 可以帮助写实现、补测试、读轨迹和提出候选解释，但我要负责明确契约、确定验证方式、检查改动，以及判断证据能支持什么结论。

拿这个项目来说，可以具体讲三类判断。第一类是边界：默认 Host 没有操作系统隔离，进程内的插件作用域也不能防恶意代码。第二类是状态：请求超时不代表没有执行，恢复时不能盲目重试。第三类是实验：一个措辞改动八次全过，不等于已经解决所有长任务问题。

如果这些设计、审阅和实验确实是我参与完成的，我就拿代码、测试和报告展示自己的判断过程。如果其中某个模块主要由其他人完成，我会说明自己负责的部分。面试里最有说服力的，是能解释为什么这样设计、哪里会失败、证据在哪，以及给一个新的边界条件能不能继续推理。

**47．岗位要求深度使用至少两款 AI 编程工具，这一段怎样准备？**

这一段必须用真实经历填。我会准备两个具体任务，分别说明在哪款工具里完成、我给了什么上下文、让它做了哪部分、哪里需要人工纠正，以及最后怎样验收。单纯列出工具名字和使用频率，不足以证明它已经融入日常。

可以采用这样的口语结构：“我日常主要用的是〔工具甲〕和〔工具乙〕。在〔真实任务〕里，我先给出目标、约束和验收方式，让它阅读相关文件再提出实现；当它在〔具体问题〕上出错时，我提供失败证据，把任务收敛到可验证的小改动。最后通过〔实际检查〕确认结果。两款工具的选择主要取决于〔自己实际观察到的差异〕。”

这些括号需要填自己的例子，不能拿项目代码反推个人使用史。如果暂时没有第二款工具的深入经历，就诚实说明使用程度，再用已经做出的产品和对工程细节的理解证明能力。也不要把不同工具背后的模型能力、交互方式和 Harness 行为混成一个笼统的好用或不好用。

**48．你如何把一个想法用 Agentic Engineering 做成可交付的东西？**

我的方法会从一个可观察的用户结果开始，再把结果拆成能验收的小步骤。例如不是先写“做一个智能编码助手”，而是先定义：给定一个工作区和修改要求，用户能够看到操作、批准必要写入、得到真实状态，并在失败后查到原因。

实现时先打通最小链路，再围绕真实暴露的失败补机制。对清晰、相互独立的子任务，可以并行让 AI 做阅读、实现或审查；共享接口和文件则要明确责任，避免多个修改互相覆盖。关键契约、权限边界和结论仍然由我检查，不把多开几个 Agent 等同于更好的工程方法。

交付也不止是测试通过。我会准备启动步骤、环境要求、可复现样例、失败说明和使用入口。对于这个项目，CLI、示例、日志查看和失败工作台就是可用性的一部分。下一阶段还需要真实试用反馈，观察用户是否理解审批、是否能恢复任务、是否愿意继续把工作交给它。

**49．如果现场只有十分钟展示，你会怎么安排？**

我会围绕一条容易理解的任务展示完整过程。先说明目标文件和保护文件，让面试官知道正确结果是什么；再展示 Agent 如何读取、提出修改、请求审批以及更新最终状态；最后打开对应的调用轨迹，说明结果不是只靠模型口头声明。

之后用已保存的 GM-D19 失败材料展示相反情况：同样是 completed，但没有工具调用，目标文件也没有达到要求。把成功和失败放在一起，更容易说明为什么需要独立验收，以及这套系统能帮我们定位哪一层出了问题。

现场如果没有真实模型凭据或网络不稳定，可以演示明确标注的离线链路，再展示已有真实评测报告。两者不能混说。项目目前主要是 CLI 和本地分析页面，没有完整 Web 产品，我会展示实际可运行的入口，而不会临时描述一个尚不存在的前端。若要演示命令执行，还应提前确认所选隔离后端是否支持该命令需要的进程能力。

**50．这个项目最大的不足是什么，你下一步优先做什么？**

最大的不足是，已经有比较完整的运行和诊断基础，但还没有证明真实用户会持续使用，也没有实现岗位里所有方向的产品能力。动态路由、跨会话记忆和主动任务都还有明确空缺，当前评测也主要是十个父家族的公开变体。

我会先解决会影响信任的问题：澄清已经发现的评测契约，在范围明确的任务上接入完成检查，覆盖合法无需修改、实际拒绝、未知副作用和保护文件变化这些反例。然后引入未参与调试的新任务和小范围真实试用，判断哪些问题最常见、最影响交付。

在这个基础上，再根据成本与使用数据选择路由或记忆方向。比如用户经常重复解释稳定项目约束，就优先考虑可纠正的项目记忆；如果大量任务难度差异明显，而且有可靠验收，就优先做路由。这样每次新增能力都有明确需求和评估方式，而不是把岗位关键词各做一个演示就算完成。

如果面试官最后问我和岗位的匹配点，我会回答：“我现在最扎实的部分，是把 Agent 的执行、上下文和评测连起来，并且能根据失败证据调整工程决策。我还没有把路由、长期记忆和主动智能全部做完，但我能说明它们接在哪里、用什么指标验证，以及哪些边界必须保留。我希望在真实用户场景里继续把这些能力做成可以使用、也能够持续改进的产品。”
