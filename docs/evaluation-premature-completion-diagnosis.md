# “未修改却说完成”的对照实验与改进方案

2026-10-03 完成两轮真实 API 实验，共 **74 次首轮试验、6 次条件性续接、237 次 API 请求、385,774 tokens**。沿用官方 DeepSeek API 的 deepseek-flash，thinking=false，其他模型参数与原基线相同。

最有支持的改进是：**把实际完成操作明确写成回复 completed 的前提。** 单加“最终回复”效果有限；单独删除摘要中的“前两轮已完成”也没有改善证据。完整历史可以缓解该问题，说明影响与上下文表达有关，但不能据此断言模型内部究竟如何理解了指令。

本次新增诊断脚本、实验性续接原型和文档。没有修改生产 agent、原始题面、GT、原基线或其分数。原样本的失败记录仍有效；以下实验属于单独的开发诊断，不是重算原基线。

## 实验如何控制变量

主要样例是 GM-D19 第三轮：dev.json 的 timeout 当前为 30，最新用户要求改成 10，prod.json 的 timeout=60 必须保持不变，修改前重读，不执行命令，完成后返回 JSON。

- 从原 GM-D19 第 1 次日志取得第三轮的真实请求，以及压缩前已经成功完成前两轮的完整消息前缀。固定前缀后重放第三轮，不重新采样前两轮，避免上游行为波动干扰定位。
- 每次首轮试验创建独立的 Runtime、Session 和合成工作区。当前文件与原成功第二轮后的状态一致；所有变体使用同一工具 schema、权限策略和隐藏 grader。
- 原样组首个 API 请求与原失败请求做深度比较，只有工作区绝对路径不同。所有组首个请求都与预先保存的变体逐项核对。
- 六组以固定随机种子在每个重复块内交错执行，每组 8 次；第二轮在观察第一轮结果后另立计划，属于探索性后续实验，保留同期原样对照。
- 不设置温度或服务端 seed，不做 SDK 自动重试，不启用命令工具。first-attempt 结果与追加续接分别计分。
- 独立 grader 仅在 agent 结束后运行，不发送给模型。续接反馈由公开任务目标的本地状态检查触发，不向模型提供隐藏判据或参考解。

这套重放检验的是模型看到的历史表达与当前指令，并没有重跑摘要生成过程。原场景本来使用固定人工摘要，因此不能把结果解释为模型自主压缩质量的评价。

## 第一轮：48 次实验

原始最后一句：

> 只返回 JSON {"status":"completed"}；不得执行命令。

| 组别 | 唯一改动或干预 | 首轮通过 | 目标状态正确 | 首个响应直接停止 |
| --- | --- | ---: | ---: | ---: |
| original | 固定摘要 + 原题面 | 2/8 | 2/8 | 6/8 |
| final-after-action | 改为“完成上述修改后，最终回复只返回 JSON…” | **8/8** | 8/8 | 0/8 |
| remove-completed-history | 只删摘要中的“前两轮已完成，” | 1/8 | 1/8 | 7/8 |
| both-wording | 同时进行上述两处措辞修改 | 8/8 | 8/8 | 0/8 |
| full-history | 原题面不变，使用压缩前完整历史 | 8/8 | 8/8 | 0/8 |
| explicit-actions | 明确目标路径及“读取→修改→成功后回复” | 7/8 | **8/8** | 0/8 |

explicit-actions 唯一失败发生在第 6 次：文件已经正确改成 timeout=10，但最终 JSON 外增加了英文说明。因此这是回复合约失败，不能混入“不执行”计数。

原样组 6 次失败和删除历史完成字样组 7 次失败，均是首个响应直接返回 completed、没有工具调用，目标文件保持 30。没有发生写调用失败、工具被隐藏、最新请求漏传或上下文超限。

“前两轮已完成”会独立诱发收尾的先前假设，在这组对照中没有得到支持。2/8 与 1/8 的小差异不能用来宣称删除这句话反而有害。完整历史与摘要的比较改变了消息内容、角色序列和长度，不能进一步区分究竟哪个历史成分起作用。

## 第二轮：拆开两处措辞，并在 port 场景复核

第一轮的有效改动同时包含“完成上述修改后”和“最终回复”，所以第二轮分别测试这两个因素。

| GM-D19 条件 | 具体措辞 | 通过 | 首个响应直接停止 |
| --- | --- | ---: | ---: |
| 同期原样 | 只返回 JSON… | 0/6 | 6/6 |
| 只限定回复阶段 | 最终回复只返回 JSON… | 2/6 | 4/6 |
| 只明确完成前提 | **完成上述修改后，只返回 JSON…** | **6/6** | 0/6 |

在本轮受控场景中，显式加入“完成上述修改后”表现最好；只加“最终回复”没有稳定消除提前停止。这提供了“完成条件的表达是重要可控因素”的实验支持，但没有读取或证明模型的内部理解过程。

随后使用另一份固定历史前缀 GM-D04：dev.port 当前 4100，要求设为 **0**，prod.port=80 不变。原样组通过 **2/4**，改为“完成上述修改后，最终回复只返回 JSON…”通过 **4/4**。这说明改进不只在 timeout 改回 10 的那一题有效；两题仍属于有限的配置续接场景，不能据此宣称普遍解决。

样本很小：即使 8/8 全通过，独立同分布假设下的 95% Wilson 区间下界也仅约 67.6%；6/6 的下界约 61.0%。服务端缓存、时间和相同题目前缀也可能使重复试验相关。第二轮是根据第一轮结果选择的探索性实验，不报告事后挑选的“显著性结论”。

## 状态检查后的有界续接

第一轮原样组的 6 次失败，各追加一次同一 Session 内的新用户轮次：

> 完成检查未通过：目标文件仍未满足最新用户请求。请重新读取目标文件，继续按最新请求完成必要操作；只有成功后才返回约定的最终 JSON。其他文件保持不变，不得运行命令。

触发条件仅依据公开任务可得的事实：run 已正常结束，但目标状态尚未满足；其他文件保持不变，且没有实际审批拒绝。未知执行状态、保护文件已被改动或实际审批拒绝，不进入该续接分支。

结果：**6/6 修复成功**，但每次额外使用 **4–5 个 API 请求**，合计 27 次请求、41,944 tokens、24.88 秒追加执行时间。首次失败没有被覆盖，也没有把“追加一次后成功”当成同预算的首轮通过率。

这是实验驱动在 run 结束后的“检测＋补救”原型，尚不是生产 agent 内部的结束检查。它也不是通用完成判断器：本实验的目标路径、字段和期望值来自明确的公开配置修改要求；一般编码任务需要另行定义可验证的公开完成条件。

## 可以确认什么，仍不能确认什么

| 判断 | 证据与边界 |
| --- | --- |
| 模型在动作选择处提前停止 | 失败请求的第一个响应就是 completed，工具调用为空；文件目标未满足 |
| 最新任务和必要状态已提供 | 原始请求、变体首个请求均已审计；目标值、目标文件和工具在输入中 |
| 回复措辞会改变本场景的执行结果 | 交错对照中，加入操作完成前提后表现明显改善；第二题方向一致 |
| 完整历史可以缓解 | 同样原始措辞下，完整历史组 8/8；无法单独归因于信息量、角色结构或最近一次工具轨迹 |
| 摘要中“已完成”是主要原因 | **未获支持**；单独删除没有改善证据 |
| agent 缺少修改能力 | 不符合本次观察：澄清条件、恢复完整历史或提供反馈后都能完成同一文件修改 |
| 模型把 JSON 模板误当成全部任务 | 与现象一致的解释，**不是已经证实的内部推理事实** |

从工程角度，可归纳为两个有证据的薄弱点：指令对“执行完成”和“输出 completed”的先后关系表达不足，在该摘要上下文下影响动作选择；harness 对模型停止缺少独立的业务完成检查，使错误声明直接成为 run 的 completed。

现有 [agentLoop 结束分支](../src/agent/loop.ts#L127) 在模型没有工具调用时接受结束。系统提示已经禁止宣称未执行的修改，说明仅有原则提醒并不足以防住这些案例。修复需要同时改善当前任务表达和完成结果的核验方式。

## 改进方案

### 1. 先采用本次有直接实验支持的措辞

建议新版本配置修改任务采用：

> 把 dev.json 的 timeout 设为 10，修改前重新读取文件；其他文件保持不变。完成上述修改后，最终回复仅包含 {"status":"completed"}。该格式要求只约束最终回复，不限制必要的工具调用。未完成时不得声明 completed。

实验直接验证的是最小改动“完成上述修改后，最终回复只返回 JSON…”。上面额外解释句是建议，尚未作为整体进行 API 验证，不能冒称该完整文案已通过。本次不修改冻结题目；应通过新的数据/协议版本发布措辞变更，并同时保留旧题面作为诊断回归，以区分措辞收益与 agent 自身稳健性收益。

不建议仅删除“前两轮已完成”作为主要修复，也不建议为了这两题一律关闭压缩。完整历史能缓解，但第一轮平均总 token 约 10,772/次，而条件化最终回复组约 5,372/次；这是本场景的实测开销，不代表一般任务的成本比。

### 2. 在 harness 内部区分“停止生成”与“业务完成”

对于能够声明公开完成条件的任务，建议由可信调用方提供目标与保护范围，结束前本地检查；模型只提出完成，harness 决定是否接受。

| 观察结果 | 建议处理 |
| --- | --- |
| 目标已经满足，保护范围无变化 | 可以接受完成，允许无需写入的合法 no-op |
| 目标未满足，执行状态确定且没有审批拒绝 | 提供实际状态反馈，最多允许一次续接；保留首次结果和新增成本 |
| 实际审批拒绝 | 停止写入，返回真实拒绝状态；不能用续接绕过拒绝 |
| 写入状态未知、保护范围被改动或检查出错 | 停止并要求核对，不自动重放写操作，也不宣称成功 |

检查应位于 `finish("completed", …)` 之前。当前模型文字通过流式事件输出，生产实现还需避免把尚未核验的 completed 展示为已确认成功；原始模型提议可以保留在日志中。

检查必须来自公开业务要求，而不是把隐藏测试答案注入模型。通用编码场景只能检查具备可信证据的属性，不能用“调用过 write_file”替代正确性，也不能强制每个任务都写文件。本次只验证了窄范围配置目标检查和一次续接的可行性，尚未实现生产接口。

### 3. 摘要中明确历史、当前状态和未完成事项

建议摘要结构分别记录“已完成历史、可验证当前状态、持续约束”；当前用户任务单独表达，避免把历史完成状态当成最新任务完成凭据。该结构化摘要方案尚未单独测试，优先级低于已得到实验支持的完成前提措辞与状态检查。

### 4. 按状态与回复分别验收

后续回归至少覆盖：摘要后修改、设为 0、改回初始值、目标已满足无需写、真实审批拒绝、非法工具参数、写入状态未知、保护文件变化，以及“文件正确但 JSON 格式错误”。同时报告首轮成功率、无依据完成声明率、续接触发/成功率、额外请求和 tokens。不能只报告最终一次成功。

本次本地测试覆盖了变体因子隔离、交错顺序、合法 no-op、不完整/越界状态、实际拒绝时不续接，以及真实 Runtime 中首次失败记录与补救结果分离，共 **5 项通过**。生产完成检查的完整回归矩阵仍需随实现补齐，不能将这些诊断测试等同于已完成生产修复。
